# 旅程图 Playbook（journey-map-playbook）

把"用户怎么用"从流程图变成一条带情绪的证据链。旅程图回答的不是"系统有几个页面"，而是：**用户在每个阶段想做什么、碰到了什么、感觉如何、哪里值得改**——情绪低谷与痛点的交汇处，就是产品机会的坐标。

使用本 playbook 前，先过数据量护栏（见「质量护栏」第 1 条）。**独立数据点不足 5 个时，只能产出整体标注"待验证"的假设旅程图。**

---

## 一、输出模板（逐字可模仿）

复制以下模板逐节填充。每个单元格的信息都必须带**来源**与**置信度**两枚标注，来源 ∈ {访谈， 数据， 假设， 合成}，置信度 ∈ {High, Medium, Low}（口径与 persona-playbook §置信度三级一致）。没数据的单元格**留空**，只写"（信息不足）"，禁止编造填充。

### 1. 旅程图主表

```markdown
# 用户旅程图：[场景一句话描述，如"外卖骑手完成一单配送"]

- 创建日期：YYYY-MM-DD
- 关联画像：[对应 persona 名称；无画像时注明"基于零散材料，未绑定画像"]
- 独立数据点计数：N 个（访谈 X 次 / 评论 Y 条 / 数据 Z 份）
- 性质：实证旅程图（或：假设旅程图——整体待验证，见质量护栏第 1 条）

| 阶段 | 用户行为（意图 → 操作 → 反馈） | 触点 | 想法 | 情绪 | 痛点 | 机会点 |
|---|---|---|---|---|---|---|
| 1. [阶段名] | 意图：___ → 操作：___ → 反馈：___ | 产品内：___；产品外：___ | "___" | +1 | ___ | ___ |
| 2. [阶段名] | 意图：___ → 操作：___ → 反馈：___ | 产品内：___；产品外：___ | "___" | -1 | ___ | ___ |
| … | … | … | … | … | … | … |

情绪曲线：[阶段1][分值] → [阶段2][分值] → [阶段3][分值] → [阶段4][分值] → [阶段5][分值]
- 情绪高峰：[阶段名]（分值 +N），原因：___
- 情绪低谷：[阶段名]（分值 -N），原因：___
```

### 2. 字段填写规则

- **阶段**：按时间顺序拆 4-9 个阶段（护栏第 2 条）。阶段名用用户视角的动宾短语（"取餐""结算收入"），不用系统视角名词（"订单模块""支付子系统"）。
- **用户行为**：必须拆成**意图 → 操作 → 反馈**三件套，缺一不可。意图是"想达成什么"，操作是"实际做了什么动作"，反馈是"系统/环境给出了什么可感知的结果"。写法示例：`意图：想省钱 → 操作：比价三家 → 反馈：看到价格表`。
- **触点**：分行写清两类——**产品内触点**（App 页面、推送、客服入口等）与**产品外触点**（微信群、同行口口相传、线下告示、天气等），两类不得混写。
- **想法**：该阶段用户脑子里的一句话，用引号包裹、第一人称，优先逐字引用用户原声。
- **情绪**：用 -2 到 +2 五档分值标注，口径固定：
  - `+2` 惊喜：超出预期的正向体验；
  - `+1` 顺畅：符合预期、无阻碍；
  - `0` 平淡：无感、例行公事；
  - `-1` 摩擦：有阻碍但能自己解决；
  - `-2` 崩溃：无法自行解决，考虑放弃或已经放弃。
- **痛点**：该阶段的具体障碍，优先用用户原话逐字引用。
- **机会点**：针对痛点的产品机会，一句话写清"为谁在哪个环节改善什么"。**写不出机会点的阶段标注"信息不足"，禁止编造**（护栏第 3 条）。

### 3. 情绪曲线（文字化画法）

主表下方必须附一行文字化情绪曲线，格式固定为 `阶段名[分值] → 阶段名[分值] → …`，随后标注高峰与低谷各一处并说明原因。示例：

```text
情绪曲线：开工0 → 接单-1 → 取餐-2 → 配送-1 → 结算+1
- 情绪低谷：取餐（-2），原因：出餐慢且无法预判，骑手的配送时限却在照常倒计时。
- 情绪高峰：结算（+1），原因：日结到账即时可见，是全天唯一明确的正向反馈。
```

曲线分值必须与主表"情绪"列逐格一致，禁止两套数。

### 4. 最小操作节点模型与竞品对标字段映射

"用户行为"列的**意图 → 操作 → 反馈**三件套即最小操作节点模型。该模型与 product-strategist（路向明）竞品对标的节点拆解**字段兼容**，两份产物可直接拼接对比——我方一行、竞品一行，逐字段对齐。映射表如下，禁止改动字段名：

| 本旅程图字段（我方现状锚点） | 竞品对标字段（路向明侧） | 对齐说明 |
|---|---|---|
| 意图 | 对标任务目标 | 用户在该节点想达成的事，双方描述同一层级的目的 |
| 操作 | 操作步骤 | 用户实际执行的动作序列，可逐动作对比步数与成本 |
| 反馈 | 结果呈现 | 系统/环境给出的可感知结果，可对比呈现形式与时效 |

拼接对比时，以"意图 ↔ 对标任务目标"为行键对齐我方与竞品的同一节点，再横向比较"操作"的步数差异与"反馈"的呈现差异；差异即竞品优势点或我方改进点。

## 二、质量护栏（可检查的清单）

交付旅程图前逐条自查，任何一条不满足即判不合格。

### 1. 硬门槛：数据点不足只能产出假设旅程图

**同一旅程对应的独立数据点少于 5 个时，禁止产出实证旅程图**，唯一允许的产出是"假设旅程图"：模板照用，但文档头部"性质"字段必须写明"假设旅程图——整体待验证"，且全部来源标注降级为"假设"。数据点计数口径与 persona-playbook 一致：一次访谈、一份问卷、一条评论各算一个，同一来源多次出现不重复计数。

假设旅程图不是废品：它是给 growth-validator（季小步）的待验证假设来源。但必须让读者一眼看出它未经实证——**把假设伪装成实证旅程图，比没有旅程图更危险**。

### 2. 阶段拆分粒度：4-9 个为宜

- **少于 4 个阶段**：合并过粗，情绪曲线退化为一条直线，痛点无处安放——必须按"意图是否变化"再拆。
- **多于 9 个阶段**：失焦，读者抓不住主干——把相邻且意图相同的阶段合并。
- 拆分判据：意图变化即换阶段；同一意图下的多个动作留在同一阶段的"操作"里展开。

### 3. 每个阶段至少一个机会点，写不出就标"信息不足"

机会点是旅程图的交付价值所在。逐阶段检查：痛点列非空而机会点列为空时，先尝试从痛点反推；确实推不出的，写"信息不足"并转入未决问题，**禁止为了表格好看编造机会点**。

### 4. 触点必须区分产品内 / 产品外

产品外触点（同行建议、微信群、天气、平台规则公告等）往往是情绪的真正来源，也是产品无法直接控制、需要设计绕行的部分。两类混写即判不合格。

### 5. 来源与置信度标注（口径与 persona-playbook 一致）

- **High**：3 个以上独立信源主动提及（未经引导自发说出）。
- **Medium**：2 个独立信源，或仅在引导后提及。
- **Low**：单一信源，待验证。
- **合成用户 panel 来源的内容永久封顶 Low，且来源标注必须写明"合成"，单独成段呈现，禁止与真实材料混排**——合成证据只用于生成待验证假设。

### 6. 情绪分值纪律

- 五档口径固定（+2 惊喜 / +1 顺畅 / 0 平淡 / -1 摩擦 / -2 崩溃），不自创档位、不用小数。
- 分值必须有依据：来自用户表述、行为数据或明确标注的假设；禁止为了画出"好看的微笑曲线"而调整分值。
- 文字化情绪曲线与主表情绪列必须逐格一致。
- 高峰与低谷必须各标注一处并写明原因；全程平直（全 0）的旅程图视为证据不足，退回补材料。

### 7. 引用与隐私纪律

- "想法"与"痛点"列的用户原声逐字引用，不润色、不改写。
- 区分"用户说的"和"用户做的"——两者矛盾时同时呈现并标注。
- 个人身份信息（姓名/手机号/账号）在输出中脱敏。

## 三、团队衔接与回传契约

### 衔接约定（旅程图为谁取材）

- **product-strategist（路向明）**：旅程图主表即"我方现状锚点"，其"用户行为"列的三件套与竞品对标节点拆解字段兼容（映射表见 §一.4），可直接拼接对比。
- **requirement-analyst（柯明澈）**：情绪低谷阶段的痛点与原声，供其 6 维访谈提纲的"用户维度"取材——低谷即访谈必问题。
- **growth-validator（季小步）**：全部"假设"来源的单元格、标注"信息不足"的机会点、假设旅程图整体，汇总为**待验证假设清单**，供其收敛 MVP 验证范围。

### 回传契约

- 长产出先落盘：旅程图写入用户项目根目录 `research/user-[slug].md` 的旅程节，slug 由主理人在任务书中指定，不自创目录。
- 经 SendMessage 回传主理人 mask-team-lead，摘要固定四字段：

```text
产物路径：research/user-[slug].md
关键结论：≤5 条（建议含：情绪低谷阶段、最强痛点、Top 机会点）
未决问题：<阻塞项 / 待验证假设>
建议下一阶段输入：<需要什么、以什么形式>
```

## 四、示例片段

以下为一份实证旅程图节选（场景：外卖骑手完成一单配送；关联细分人群为午晚高峰全职骑手，独立数据点 9 个：访谈 5 次 / 应用商店评论 4 条）。注意三处正确形态：**单元格带来源与置信度**、**情绪曲线与主表逐格一致**、**节点三件套完整**。

```markdown
# 用户旅程图：外卖骑手完成一单配送

- 创建日期：2026-10-10
- 关联画像：午晚高峰在线 6 小时以上的全职骑手
- 独立数据点计数：9 个（访谈 5 次 / 评论 4 条）
- 性质：实证旅程图

| 阶段 | 用户行为（意图 → 操作 → 反馈） | 触点 | 想法 | 情绪 | 痛点 | 机会点 |
|---|---|---|---|---|---|---|
| 1. 上线开工 | 意图：尽快进入可接单状态 → 操作：打开 App、刷脸验证、点击上线 → 反馈：状态变为"听单中"（来源：访谈#01/#03；置信度：High） | 产品内：App 上线页、刷脸验证；产品外：电动车换电站（来源：访谈；置信度：Medium） | "赶紧上线，午高峰别迟到。"（来源：访谈#03；置信度：Medium） | 0 | 刷脸在强光下常失败，要反复找角度（来源：评论 2 条；置信度：Medium） | 刷脸失败时提供备选验证方式，避免开工前消耗（来源：由痛点反推；置信度：Medium） |
| 2. 接单 | 意图：接到顺路且单价合理的单 → 操作：听单、查看派单卡片、点击确认 → 反馈：显示取餐地址与配送时限（来源：访谈 4 人；置信度：High） | 产品内：派单卡片、地图；产品外：同行群里交流哪些商圈单多（来源：访谈#02；置信度：Medium） | "这单顺不顺路？不顺路接了要亏。"（来源：访谈#02 原话；置信度：High） | -1 | 派单卡片信息挤在一屏，骑车时看不清取餐距离（来源：访谈 3 人；置信度：High） | 派单卡片突出取餐距离与时限两个关键字段，支持语音播报（来源：由痛点反推；置信度：High） |
| 3. 到店取餐 | 意图：到店即取、不耗时间 → 操作：导航到店、报取餐号、等待出餐 → 反馈：拿到餐品或被告知还要等（来源：访谈 5 人；置信度：High） | 产品内：取餐号、报备按钮；产品外：商家出餐速度、店内排队（来源：访谈；置信度：High） | "又卡餐，我的时间不是时间吗。"（来源：访谈#04 原话；置信度：High） | -2 | 出餐慢无法预判，配送时限照常倒计时；报备流程入口深（来源：访谈 5 人全部提及；置信度：High） | 展示商家历史出餐时长供接单前参考；报备入口前置到取餐页首屏（来源：由痛点反推；置信度：High） |
| 4. 配送送达 | 意图：按时送到、不洒餐 → 操作：按导航骑行、联系顾客、交付 → 反馈：订单状态变为"已送达"（来源：访谈；置信度：High） | 产品内：导航、联系顾客按钮；产品外：天气、小区门禁、顾客电话是否接通（来源：访谈#01/#05；置信度：Medium） | "千万别超时，一超时这单白跑。"（来源：访谈#05 原话；置信度：Medium） | -1 | 老小区楼号混乱，导航定位常偏（来源：评论 2 条；置信度：Medium） | 信息不足——定位偏差的改善手段需技术与运营联合评估（转入未决问题） |
| 5. 收工结算 | 意图：确认今天挣了多少 → 操作：打开收入页、核对单量与金额 → 反馈：显示当日收入明细与到账状态（来源：访谈 3 人；置信度：High） | 产品内：收入页、到账通知（来源：访谈；置信度：High） | "看到钱到账，今天才算完。"（来源：访谈#01 原话；置信度：Medium） | +1 | 扣款项（超时罚款等）缺少逐笔说明，看不懂为什么被扣（来源：评论 2 条；置信度：Medium） | 扣款项逐笔附原因与申诉入口（来源：由痛点反推；置信度：Medium） |

情绪曲线：上线开工0 → 接单-1 → 到店取餐-2 → 配送送达-1 → 收工结算+1
- 情绪低谷：到店取餐（-2），原因：出餐慢不可预判且配送时限照常倒计时，骑手承担了商家侧的延误成本，5 次访谈全部主动提及（置信度：High）。
- 情绪高峰：收工结算（+1），原因：当日收入即时可见，是全天唯一明确的正向反馈（置信度：High）。
```

### 节点拆解与对标拼接示例

以"到店取餐"阶段为例，我方节点三件套与路向明侧竞品节点拆解按字段映射逐行对齐：

| 字段 | 我方（本旅程图） | 竞品 A（路向明对标产物） |
|---|---|---|
| 意图 ↔ 对标任务目标 | 到店即取、不耗时间 | 到店即取、不耗时间 |
| 操作 ↔ 操作步骤 | 导航到店 → 报取餐号 → 等待出餐（3 步） | 导航到店 → 扫码取餐柜取餐（2 步） |
| 反馈 ↔ 结果呈现 | 拿到餐品，或被告知等待（无预期时长） | 柜门弹开即取，出餐进度实时可见 |

逐字段对齐后，差异立现：竞品把"等待出餐"这一步从操作中消掉，并在结果呈现上给出实时进度——这就是对标结论的直接素材。
