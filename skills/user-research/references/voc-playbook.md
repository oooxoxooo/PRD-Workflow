# VoC 洞察方法论底稿（voc-playbook）

本文档是闻众声执行 VoC（用户之声）任务的完整操作规程。接到主理人下发的 VoC 任务后，先判断走哪种模式，再按"提取 → 综合 → 标注 → 落盘回传"的顺序执行。全文命令式语气即契约：写"禁止"就绝对不做，写"必须"就逐条满足。

统一阅读顺序：**输出模板（第一节，逐字可模仿）→ 质量护栏（第二节，逐条可检查）→ 示例片段（第三节，对照仿写）**。

---

## 第一部分 输出模板（逐字可模仿）

### 1.1 双模式框架：先判断走哪条路

VoC 任务只有两种模式，开工前用一句话向自己确认："材料在我手里，还是要我去找？"

#### 模式 1：分析已有材料

用户或主理人直接提供材料（CSV、导出文件、粘贴文本）。按材料类型确定提取重点：

| 材料类型 | 提取重点 | 特别注意 |
|---|---|---|
| 访谈记录 | 完整六要素；重点关注上下文与追问链条 | 区分"受访者主动说的"与"被访谈者引导后说的"，后者置信度降一档 |
| 问卷 | 开放题答案优先；封闭题只做分布统计，不做动机推断 | 样本自陈偏差大，结论只到"受访者声称"，不上升到"用户实际" |
| 客服工单 | 痛点、触发事件、期望结果 | 工单天然偏向"出问题的人"，不能反推整体满意度 |
| 公开评论（应用商店、社区） | 原声词汇、情感强度、高频主题 | 评论者偏向极端意见（见 2.4 偏差清单） |
| 流失访谈 / 退款原因 | 触发事件、备选方案去向、"压垮的最后一根稻草" | 流失用户的答案最诚实，优先采信其主动提及的痛点 |

#### 模式 2：主动采集

手里没有材料时，用宿主 WebSearch/WebFetch 能力去公开信源采集。按 ICP 类型选信源：

| ICP 类型 | 优先信源 | 采集要点 |
|---|---|---|
| B2B 决策者 | 知乎行业问题、行业垂直社区、公众号评论区 | 搜"选型""对比""替代"类关键词，关注采购决策链上的真实吐槽 |
| SMB / 个体经营者 | 什么值得买评论区、小红书、微博、淘宝/京东评价 | 关注"值不值""好不好上手"，价格敏感度信号密度最高 |
| 开发者 | V2EX、即刻、GitHub Issues、掘金/开源中国评论区 | 关注集成成本、文档质量、被坑经历；技术用户的原声词汇直接可进需求文档 |
| 消费者 | 应用商店评论（App Store / 各安卓市场）、小红书、微博、豆瓣小组 | 关注评分两极分化的中间地带，3 星评论信息密度通常最高 |

采集执行纪律：

1. 每次访问一个信源，立即把该 URL 记入本次会话的"已访问清单"，后续报告只允许引用清单内的 URL。
2. 每个信源摘录原文段落，连同信源名与日期一起记录，禁止凭记忆复述。
3. 信源不可访问或反爬时，标注 💡 降级说明（"该信源未实际访问，以下不含其数据"），绝不假装访问过。
4. 采集总量以"每个主题至少 2 个独立信源"为下限，达不到就按 2.5 的最小样本量规则降级为研究缺口清单。

### 1.2 统一提取六要素

无论哪种模式、哪种材料，逐条材料按以下六要素提取。某要素材料中没有，就写"未提及"，禁止脑补。

```markdown
## 材料 [编号]（信源：[来源名]，日期：[YYYY-MM-DD]，类型：[访谈/问卷/工单/评论/流失]）

- JTBD（用户雇佣产品完成的任务）：
  - 功能层：[要完成的具体事情]
  - 情感层：[想获得或摆脱的感受]
  - 社会层：[想在他人眼中成为的样子]
- 痛点：[遇到的问题；优先记录用户主动提及且带情绪语言的]
- 触发事件：[是什么让 ta 开始寻找/更换方案]
- 期望结果：[ta 心目中的"问题解决了"长什么样]
- 原声词汇：[逐字引用，禁止改写、禁止润色、禁止翻译腔加工]
- 备选方案：[ta 在用或考虑的其他做法，含"什么都不做"这一合法选项]
```

提取纪律：

- **JTBD 三层**：功能层必填；情感层与社会层材料中有证据才填，没有就标"未提及"。
- **痛点优先级**：主动提及且带情绪语言（"气死""崩溃""再也不"）的痛点排最前；引导后提及的单独标注。
- **原声词汇**：逐字引用是铁律。错别字、口头禅、方言都保留原样——它们是后续画像与文案取材的金矿。
- **备选方案**："什么都不做 / 继续用 Excel / 手工记"是合法且重要的答案，必须单独记录，不许漏。

### 1.3 置信度三级标注

每条洞察必须带置信度标签，规则机械执行，不允许自由裁量：

| 等级 | 判定条件（满足全部） |
|---|---|
| **High** | 3 个及以上独立信源支持；且用户主动提及（非引导）；且跨细分人群一致 |
| **Medium** | 恰好 2 个独立信源；或仅引导后提及；或仅在单一细分人群内成立 |
| **Low** | 单一信源；或任何待验证的推断 |

**合成用户 panel 产出的洞察，置信度永久封顶 Low**，无论"看起来"多么一致。这不是建议，是铁律：合成用户的用途只有两个——生成待验证假设、压力测试访谈提纲。任何由合成用户"验证"的结论，在交付物中必须标注"合成验证，需真实用户复验"。

**信源权重表（判定置信度时的辅助依据）**：不同信源的固有偏差不同，计数"独立信源"前先过这张表——两个高偏差同向的信源不等于两个独立视角。

| 信源 | 信号强度 | 固有偏差 |
|---|---|---|
| 用户访谈（主动提及） | 极高 | 样本小；偏向高参与度的用户 |
| 流失/成败访谈 | 高 | 只有近期记忆；常有事后合理化 |
| 应用商店差评（1-3 星） | 高 | 偏向极端情绪，爱恨分明 |
| 知乎/小红书/V2EX 等社区帖 | 中高 | 偏向爱表达的少数派；各平台人群结构偏差（见 source-guides-zh.md 各平台卡） |
| 客服工单 | 中 | 偏向问题而非价值；沉默大多数不在其中 |
| 问卷开放题 | 中 | 被题目框架引导 |
| 问卷选择题 | 中低 | 是你提供的选项的产物，不是用户自生的答案 |
| 电商评论区（什么值得买等） | 中 | 偏向价格敏感型用户；晒单有返现动机 |
| 微博/短视频评论区 | 中 | 偏向高情绪瞬间；水军与营销噪音需先过滤 |
| 招聘启事（JD） | 中低 | 是企业"期望"而非"现状"的痛 |
| 合成用户 panel | 永久 Low | 模型对"这类用户会怎么说"的想象，不是用户事实 |

**时效窗口**：12 个月内为主信源；12-24 个月谨慎使用（产品与市场可能已变）；2 年以上仅作基线背景。同一主题在新旧材料中一致出现 = 耐用品信号，值得行动。

### 1.4 综合输出模板（最终报告骨架）

```markdown
# VoC 洞察报告：[研究主题]
日期：[YYYY-MM-DD] | 模式：[1 已有材料 / 2 主动采集] | 材料量：[N 条，M 个独立信源]

## 一、事实层（用户说了什么）

> 本节只含可溯源的材料证据与统计，不含任何推断。每条洞察带置信度标签。

### 主题 1：[主题名]（频次 [X/Y 信源] | 强度 [高/中/低] | 置信度 [High/Medium/Low]）

- 摘要：[1-2 句，只概括材料事实]
- 原声引用：
  > "[逐字引用 1]"——[信源]，[日期]
  > "[逐字引用 2]"——[信源]，[日期]
- 六要素快照：JTBD […] / 痛点 […] / 触发事件 […] / 期望结果 […] / 备选方案 […]

### 主题 2：……
（主题按"频次 × 强度"排序，最强的排最前；每个主题必须带 2 条逐字原声引用）

## 二、解读层（我们认为这意味着什么）

> 本节是分析判断，每条解读必须回指事实层的主题编号，禁止无根解读。

- 解读 1（基于主题 1、3）：[推断]，置信度 […]，[如为推断则标注"假设待验证"]
- 启示：[对产品/需求/验证的具体启示]

## 三、合成用户 panel 补充（如有）

> 本节仅在执行过合成 panel 时出现，与上面两节物理隔离，禁止混排。
> 本节全部洞察置信度封顶 Low，统一标注"合成验证，需真实用户复验"。

## 四、研究缺口与下一步

- 数据不足、无法下结论的问题清单
- 建议下一阶段输入（供 requirement-analyst / growth-validator 取材）
```

格式硬规则：

- 主题排序唯一标准：**频次 × 强度**，不许按"我觉得重要"排。
- 每主题 **2 条逐字原声引用**，带信源与日期；引用字段缺失或 URL 不在本会话已访问清单内，整份报告判不合格。
- **事实层与解读层必须分节**，解读层每条回指事实层编号；两节混写判不合格。
- 合成 panel 产出**单独成节**，禁止与真实材料混排。
- 信息不足处统一标注"假设待验证"，禁止把假设写得像事实。

### 1.5 与 voc_pipeline.py 的衔接

材料量大时（几十条以上），先跑确定性预处理脚本，再做语义工作：

```bash
python3 ../scripts/voc_pipeline.py --input feedback.csv --text-col content --out voc/
# 产出：voc/cleaned.jsonl（脱敏后原文）+ voc/themes.json（主题词频聚类草稿）+ voc/quotes.md（候选原声库）
```

职责边界，机械执行：

- **脚本做的**：清洗、去重、脱敏（手机号/身份证/邮箱/银行卡号/中文姓名的正则掩码，不可逆）、主题词频聚类草稿、情感粗标、候选原声排序。
- **你（LLM）做的**：在脚本草稿之上做语义归并（合并脚本拆碎的主题、拆分脚本粘在一起的主题）、为主题命名、从候选原声库里挑选 money quotes、写洞察与解读。
- **脚本草稿不进最终报告**：themes.json 是工作底稿，报告里的主题必须是你归并命名后的结果。
- 脚本脱敏是兜底，不是免责——你在报告中仍须自查一遍无个人身份信息残留。

### 1.6 回传契约

VoC 报告是长产出，执行以下流程，一步不许省：

1. **落盘**：写入用户项目根目录 `research/user-[slug].md`，slug 由主理人在任务书中指定；未指定时先问主理人，不自创目录、不自造 slug。
2. **回传**：通过 SendMessage 回传主理人 mask-team-lead，**不直接输出给用户**。回传摘要固定四字段，逐字格式：

```
产物路径：research/user-[slug].md
关键结论：≤5 条，每条一句话
未决问题：阻塞项 / 待验证假设清单
建议下一阶段输入：需要什么、以什么形式（如：供 requirement-analyst 取材的痛点清单 / 供 growth-validator 的假设列表）
```

3. 落盘文件是完整报告；回传消息只含路径与摘要，不粘贴全文。

## 第二部分 质量护栏（逐条可检查的清单）

交付前逐项打勾。任何一项不过，回到对应环节修正后再交。

### 2.1 幻觉 URL 铁律（最高优先级，不可违反）

- [ ] 报告中出现的每一个 URL，都存在于本会话"已访问清单"中——即本会话用 WebSearch/WebFetch 实际访问并成功读取过。
- [ ] 禁止输出任何"我记得存在""应该存在""典型如"的 URL。记不清 = 没访问过 = 不许写。
- [ ] 无法溯源的引用，要么重新访问补证，要么删除，要么标注"来源未能核实"。
- [ ] 报告模板中 URL/信源字段为空即判不合格，不允许"略"。

### 2.2 来源与标注

- [ ] 公开材料逐条注明来源（信源名 + 日期 + URL 或材料编号）。
- [ ] 信息不足处全部标注"假设待验证"，全文搜一遍，无漏标的推断伪装成事实。
- [ ] 每条洞察带置信度标签（High/Medium/Low），且判定严格按 1.3 的机械规则。
- [ ] 合成用户产出全部封顶 Low，单独成节，逐条标注"合成验证，需真实用户复验"，与真实材料零混排。

### 2.3 六要素完整性

- [ ] 每条材料按六要素提取，缺失要素标"未提及"而非编造。
- [ ] 原声词汇全部为逐字引用，无润色、无改写、无错别字修正。
- [ ] 备选方案字段含"什么都不做/维持现状"类答案（若材料中存在）。
- [ ] 主动提及的痛点与引导后提及的痛点已区分。

### 2.4 样本偏差检查清单（下结论前必过）

- [ ] **极端意见偏差**：评论者偏向"极好/极坏"两极，沉默的大多数不在样本里——结论措辞限定为"评论者中"，不外推为"用户中"。
- [ ] **工单偏差**：客服工单反映的是"出问题的人"，不能从中提取"用户重视什么价值"，只能提取"哪里会出问题"。
- [ ] **平台人群结构偏差**：小红书偏一二线年轻女性、V2EX 偏一线开发者、知乎偏高学历男性——结论注明"样本来自 [平台]，人群结构偏向 […]"。
- [ ] **时效窗口**：12 个月内的信源权重更高；超过 12 个月的材料单独标注日期，结论若依赖旧材料须提示时效风险。
- [ ] **最小样本量**：独立数据点少于 5 个时，禁止画像、禁止下结论，只产出"研究缺口清单"（已知什么、缺什么、建议怎么补）。

### 2.5 结构与契约

- [ ] 主题按"频次 × 强度"排序，每主题含：摘要（1-2 句）/ 频次（X/Y 信源）/ 强度（高中低）/ 2 条逐字原声引用（带信源与日期）/ 启示。
- [ ] 事实层与解读层分节，解读逐条回指事实层主题编号。
- [ ] 长产出已落盘 `research/user-[slug].md`；回传四字段齐全；经 SendMessage 发主理人，未直接输出给用户。
- [ ] 脚本草稿（themes.json 原始内容）未混入报告。
- [ ] 全文无个人身份信息残留（脚本脱敏后人工复查一遍）。

## 第三部分 示例片段（对照仿写）

以下为"记账 App 评论分析"任务的片段演示：模式 1（用户提供应用商店评论导出），共 27 条评论、3 个独立信源。完整报告含 3 个主题，此处完整展示排名第 1 的主题块，并演示事实/解读分层与置信度标注。

```markdown
## 一、事实层（用户说了什么）

### 主题 1：记一笔的步骤太多，坚持不下来（频次 3/3 信源 | 强度 高 | 置信度 High）

- 摘要：三个信源中均有用户主动抱怨"记账动作链路太长"，且多处伴随强烈情绪语言；
  这是全部材料中出现频次最高、情绪最强的主题。
- 原声引用：
  > "记一笔账要点四下，还要选分类，记到第五天我就放弃了，真的坚持不下去"——应用商店评论（信源 A），2026-08-14
  > "每次买完东西想到要打开 app 填一堆就头疼，后来干脆不记了"——问卷开放题（信源 B），2026-09-02
- 六要素快照：
  JTBD 功能层=快速记录日常收支；情感层=摆脱"记账是件麻烦事"的挫败感；社会层=未提及；
  痛点=记录链路长导致中断（主动提及，带情绪）；触发事件=多次漏记后账目对不上；
  期望结果="随手一下就记完"；备选方案=放弃记账（"什么都不做"）、改用微信账单导出的表格。

（主题 2、主题 3 略——实际报告中按"频次 × 强度"依次完整展开，结构与本块逐字一致。）

## 二、解读层（我们认为这意味着什么）

- 解读 1（基于主题 1）：该产品的核心流失点可能不在功能缺失，而在记录动作的摩擦成本；
  缩短"记一笔"的步数优先级应高于新增报表功能。置信度 Medium——评论样本偏向已流失或
  濒临流失的用户（见样本偏差检查），"假设待验证"：建议用留存数据交叉验证。
- 启示：供 product-strategist 对标时重点查竞品的"快速记账"交互；供 growth-validator
  的 MVP 假设清单加入"一键记账可将 7 日留存提升至 X%"。
```

示例要点对照（仿写时逐项核对）：

- 主题名是一个**用户语言表述的结论**（"步骤太多，坚持不下来"），不是分类学名词（"易用性问题"）。
- 频次写成 `X/Y 信源` 的具体数字，强度只在高/中/低中选，置信度标签紧跟着。
- 两条原声引用逐字保留原文（包括口语"app""头疼"），各带信源与日期。
- 事实层零推断：摘要只说"材料里有什么"；解读层才出现"可能不在…而在…"并回指主题编号、自带置信度与"假设待验证"。
- 备选方案里"什么都不做"被显式记录。
